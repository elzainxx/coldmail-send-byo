# config-consumers.txt — the Config Consumption Sweep's permanent ledger (Phase 9.5 CLOSEOUT,
# 2026-07-27). One line per seeded send_byo.config key (must match config-manifest.txt exactly, in
# any order): a real dial cannot pass config_drift alone — it must ALSO have a genuine consumer
# cited here, or be explicitly marked RESERVED (never both silent AND passing).
#
# Format: key|grep-ERE-pattern-proving-consumption
#     or: key|RESERVED|<expiry-gate-or-phase>
#
# The pattern is checked by tests/harness/checks/config_consumption.sh with:
#   grep -rlE '<pattern>' --include=*.go --include=*.js <repo root> \
#     | grep -vE '_test\.go$|/dispatch/config\.go$|/adminapi/config_validate\.go$'
# i.e. it must appear SOMEWHERE OTHER than the loader (dispatch/config.go), the write-time
# validator (adminapi/config_validate.go), or a test file — a genuine runtime consumer, not just
# "this key is known to exist." RESERVED entries additionally require the literal marker
# "RESERVED / NOT-YET-CONSUMED" to appear in Docs/config-reference.md for that key (checked
# separately) — so a key cannot be silently downgraded to RESERVED without a documented reason an
# operator can actually read.
#
# RESERVED expiry (M3-P2-OD-8, ruled 2026-07-31): the third field is REQUIRED and names the
# gate/phase by which the marker must be gone — checked against Docs/current-phase.txt. A marker
# whose expiry has passed fails the gate, so the hatch cannot quietly become permanent. The two keys
# that motivated the field, retry_count_4xx and variation_zero_width_rate_pct, were both found
# RESERVED with no expiry by accident during a Phase 9.5 review sweep — exactly the failure mode it
# exists to close. Both have since been DISCHARGED: the field fired for real at Phase 8's
# current-phase.txt bump and both keys were DROPPED at send_byo_0049 (M3-P8-OD-8, ruled 2026-08-04),
# so the mechanism is now proven end to end, from accidental marker to actual disposition.
#
# THE FW-EXPIRY FORM IS WITHDRAWN — ruled 2026-08-05. The third field accepts a gate/phase label
# ONLY. From 2026-08-04 it also accepted a future-work item id (FW-M3-N), added by M3-P8-OD-8 so that
# score_alert_threshold — the last phase having arrived, with its consumer still wanted — could keep a
# marker that did not lie about a date. The ruling is that this was the wrong trade:
#
#   Re-pointing a RESERVED expiry at an OPEN-ENDED future-work item is the "RESERVED becomes
#   permanent" failure the time-boxing rule exists to prevent.
#
# The mechanism bears that out. A phase label expires BY ITSELF when the tree reaches that phase,
# whether or not anyone remembers it. The FW form's only check is that a heading still exists in
# future-work.md — and a heading is trivially kept forever, so the marker satisfies its own gate on
# every run while never coming due. It kept the jaw and removed the teeth.
#
# score_alert_threshold was the only key ever on that form, and it was DROPPED at send_byo_0051 rather
# than re-marked. THERE IS NO RESERVED KEY IN THIS LEDGER NOW. The feature it was seeded for is not
# cancelled: FW-M3-12 stands in Docs/future-work.md, and the key returns ADDITIVELY in the same change
# that lands its consumer — ADR-0016's own discipline (seed at real consumption, never before), which
# also means it can never be a Rule 1 violation in the gap the way the seeded row was continuously.
#
# The consequence for a future key is deliberate and is the point: if the tree is at the last phase
# and a key has no consumer, there is no honest marker left to write, so the key does not get seeded
# yet. That is the rule working, not a gap in it.
#
# Maintenance rule (mirrors the ADR-0008 grants-invariant discipline): every new seeded key gets a
# line here in the SAME change that adds the migration — the gate fails a key with no line at all,
# so a key can never silently ship undocumented-as-to-consumption.
